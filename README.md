## 1. 简介

Sonic 是一套**网页请求录制与离线回放工具**，由两个组件组成：

| 组件 | 用途 |
|------|------|
| **Sonic Creator** | 录制网页的网络请求、配置回放策略、预览回放效果、导出回放包 |
| **Sonic Player** | 打开 .swsonic 回放包，在离线环境下完整还原页面的网络交互 |

**典型使用场景**：

- **离线演示**：将需要联网的网页录制为回放包，在无网络环境中完整演示
- **技术交流**：录制网页交互流程，与他人分享可回放的演示包
- **协议分析**：录制并查看页面的全部网络请求细节（Headers、Body、状态码等）
- **自动化测试**：录制页面交互作为基线，后续通过回放验证行为一致性

**技术架构**：Qt 6 桌面框架 + Microsoft Edge WebView2 浏览器引擎 + Chrome DevTools Protocol (CDP) 网络拦截。

## 3. 核心概念

### 3.1 .swsonic 文件

`.swsonic` 是 Sonic 的录制回放包格式，每个文件保存了一次完整的录制会话，包含：

- **入口 URL**：录制的起始页面地址
- **资源数据**：所有 HTTP 请求及其对应的响应内容
- **策略配置**：用户定义的回放匹配规则

### 3.2 录制 vs 调研

| 对比维度 | 录制（Record） | 调研（Survey） |
|----------|---------------|----------------|
| **目的** | 完整捕获网络请求数据 | 快速了解网站网络结构 |
| **数据量** | 大（保存完整响应体） | 小（仅分析 URL 模式） |
| **用途** | 生成回放包 | 辅助制定策略 |
| **耗时** | 与页面交互同步 | 快速扫描 |

**建议流程**：先调研 → 根据调研报告制定策略 → 再录制。

### 3.3 策略匹配

回放时，Player 需要将页面发出的请求 URL 与录制包中存储的请求进行匹配。由于 URL 中可能包含**时间戳、随机 Token、动态参数**等可变部分，直接精确匹配往往会失败。

策略系统的作用就是在匹配时**忽略这些动态部分**，让回放引擎能从录制包中找到对应的响应数据。

策略按以下**扁平化优先级顺序**执行：

1. **exact**（精确匹配，含尾部斜杠变体）— 内置，始终启用
2. **protocol_swap**（HTTP/HTTPS 互换）— 内置，始终启用
3. **strip_hash**（忽略 #fragment）— 内置，始终启用
4. **用户策略**（按优先级依次尝试）
5. **content_type_fillback**（自动补充缺失 Content-Type）— 内置兜底

详见 [第 6 章 策略配置详解](#6-策略配置详解)。

### 3.4 Web 持久化存储与 Origin（源）

#### 什么是 Origin？

Web 平台上所有持久化存储（localStorage、IndexedDB、Cache API、Cookie、Service Worker 等）的隔离单位叫做 **Origin（源）**。一个 Origin 由三个要素唯一确定：

```
origin = (scheme, host, port)
```

| 示例 | 是否同一 Origin | 原因 |
|------|:---:|------|
| `https://poki.com` vs `http://poki.com` | ❌ | scheme 不同（https ≠ http） |
| `https://game.poki.com` vs `https://poki.com` | ❌ | host 不同（子域名也算不同源） |
| `https://poki.com:443` vs `https://poki.com:8443` | ❌ | port 不同 |
| `https://poki.com/game1` vs `https://poki.com/game2` | ✅ | 路径不影响 Origin |

#### 这对 Sonic 用户意味着什么？

1. **同一 Origin 内的所有页面共享存储**。例如 `poki.com` 下的多个 H5 游戏共用同一份 localStorage，玩家在游戏 A 的存档可以被游戏 B 读取（取决于游戏自身设计）。

2. **不同 Origin 之间完全隔离**。`poki.com` 的 IndexedDB 数据无法被 `crazygames.com` 访问，浏览器强制隔离。

3. **Sonic 的 WebView2 用户数据目录（UDF）包含所有访问过的 Origin 的数据**。如果你录制了 `site-a.com` 和 `site-b.com`，两个 Origin 的 localStorage、IndexedDB、Cache 等都会存储在同一个 UDF 内。

4. **清理 UDF 会删除该目录内所有 Origin 的全部数据**。Sonic 各组件使用**独立的 UDF**（见下方表格），因此 Creator 录制时的清理不会影响 Player 的存档。

> **提示**：了解 Origin 概念有助于理解为什么录制时需要清理缓存、为什么回放存档可能丢失、以及不同类型的存储（localStorage vs sessionStorage vs IndexedDB vs Cookie）的生存周期差异。

#### Sonic 各组件的 UDF（用户数据目录）

每个 Sonic 组件使用独立的 WebView2 用户数据目录，互不干扰：

| 组件 | UDF 位置 | 清理策略 |
|------|----------|----------|
| **Sonic Creator** | `%TEMP%\sonic_creator_wv2`（临时目录） | 每次启动时**清空**（保证录制环境干净，防止 SW/Cache 残留污染） |
| **Sonic Player** | `%LOCALAPPDATA%\Sonic Player\instances\__player_default\webview2`（应用数据目录） | **保留**（保证 localStorage/IndexedDB 存档跨会话持久化，且不受系统磁盘清理影响）；支持通过 **工具 → 清除缓存** 手动清除缓存数据（见 [5.2 清除缓存](#52-基本操作)） |
| **回放预览诊断**（Creator 内嵌） | `%TEMP%\sonic_diag_wv2`（临时目录） | 每次打开时清空（临时诊断环境） |

> **提示**：三者的 UDF 相互独立，你可以放心地先用 Player 积累存档，再启动 Creator 录制新内容，互不影响。Player 的存档位于应用数据目录（而非临时目录），因此系统磁盘清理工具不会误删玩家的存档。

### 4.2 工作流一：录制网页请求

**适用场景**：完整捕获一个网页的所有网络交互，生成 .swsonic 回放包。

#### 步骤 1：导航到目标页面

在 URL 地址栏输入目标网址（例如 `https://example.com`），按 **Enter** 键导航。

> **提示**：可以省略 `https://` 前缀，Creator 会自动补全。支持 `http://`、`https://`、`chrome://`、`about:`、`file://` 等协议。

> **实践建议**：建议**不要直接从目标页面开始录制**。可以先导航到更外层、非目标页面（如网站首页、列表页），再点击跳转到目标页面并完成操作。
>
> 原因：直接通过地址栏输入打开目标页面时，页面及其资源的请求缺少真实的跳转链路，且请求头中通常**没有 Referer**（地址栏直达不会携带）。部分网站存在边界条件或会**校验 Referer**，从外层页面点击进入录制到的请求链更完整、更接近真实用户访问场景，回放成功率更高。

#### 步骤 2：开始录制

1. 切换到 **录制** 标签页
2. 点击 **⏺ 开始录制** 按钮（按钮变为红色，状态栏显示"录制中"）
3. Creator 会自动清理浏览器缓存、注入时间/随机数垫片，然后导航到入口页面

#### 步骤 3：操作页面

在浏览器区域正常浏览和操作网页。Creator 会自动拦截并记录所有 HTTP 请求：

- 页面加载的资源（HTML、CSS、JS、图片、字体等）
- AJAX / Fetch 异步请求
- 表单提交（POST / PUT / DELETE）
- 重定向链（301 / 302）

你可以实时在右侧面板看到请求列表的更新。

#### 步骤 4：停止录制

完成所需操作后，点击 **■ 停止** 按钮。

> **注意（Range 分片资源）**：录制期间若页面发起分片下载请求（HTTP 206），
> Creator 会以独立请求自动补发一次**完整资源下载**（用于回放）。
> 录制中状态栏会显示「分片补全 N」实时指示剩余下载数，归零即代表全部完成。
>
> 点击停止前，请在右侧监视面板确认对应资源已出现 **200 记录**
> （或在 `sonic_creator.log` 中看到 `Probe record written` 日志），
> 否则该资源的完整内容不会被保存，回放时将退回分片数据。
>
> 若停止时仍有完整资源正在下载，程序会弹出确认框，**列出每个未完成
> 下载的 URL、已等待时间与进度**——请选择 **「取消」** 等待下载完成
> （状态栏「分片补全」归零）后再停止，避免丢弃已下载的完整资源。
>
> 若服务器长时间无响应（15 秒内未收到任何数据），该下载会自动放弃并
> 在状态栏提示"分片补全失败"——对应资源回放时需手动配置策略。

录制停止后：
- 状态栏显示录制摘要（资源数、总大小）
- 工具面板按钮变为可用

#### 步骤 5：配置策略 & 保存

录制完成后，建议先进行策略配置（见 [4.4 工作流三](#44-工作流三配置回放策略)），然后保存为 .swsonic 文件（见 [4.7 保存与导出](#47-保存与导出)）。

### 4.3 工作流二：调研分析

**适用场景**：快速了解目标网站的网络结构，获取策略配置建议，为正式录制做准备。

#### 步骤 1：启动调研

1. 在 URL 栏输入目标网址
2. 切换到 **录制** 标签页
3. 点击 **🔍 调研分析** 按钮（按钮变为金色，状态栏显示"调研中"）

#### 步骤 2：等待分析完成

Creator 会自动导航并收集页面的全部网络请求 URL。通常几秒内即可完成。

#### 步骤 3：查看调研报告

调研完成后自动弹出报告对话框，包含以下内容：

| 分析项目 | 说明 |
|----------|------|
| **资源类型分布** | Document / Stylesheet / Script / Image / Font / XHR 等各类型的请求数量 |
| **域名拓扑** | 页面涉及的各个域名及其请求数 |
| **URL 模式分析** | 含 Query 参数的比例、含时间戳参数的比例、含 Hash 的比例等 |
| **策略建议** | 基于分析结果自动生成的中文策略建议 |

根据报告中的策略建议，可以更有针对性地配置回放策略。

#### 步骤 4：停止调研

点击 **■ 停止** 按钮结束调研。

### 4.4 工作流三：配置回放策略

### 4.6 工作流五：回放预览与诊断

在保存 .swsonic 文件之前，建议先通过回放预览测试录制效果和策略配置。

## 6. 策略配置详解

策略是回放匹配的核心。以下是三种用户可配置策略的详细说明。

### 6.1 QueryParams 剥离

**用途**：忽略 URL Query 参数中的动态字段（如时间戳 `ts=1719000000`、Token `token=abc123`），使回放时能够匹配。

#### 配置字段

| 字段 | 说明 | 示例 |
|------|------|------|
| **筛选模式** | URL 匹配方式 | 精确匹配 / 通配符 / 正则表达式 |
| **筛选值** | 限定 URL 路径范围 | `*/api/*`（通配符模式） |
| **忽略的键名** | 要剥离的参数名列表 | `ts`, `token`, `nonce`, `_` |

#### 示例

假设录制时请求了 `GET /api/data?page=1&ts=1719000000&token=xyz`，回放时请求变为 `GET /api/data?page=1&ts=1719999999&token=abc`。

配置：
- 筛选模式：**通配符**，筛选值：`*/api/*`
- 忽略键名：`ts`, `token`

匹配过程：
1. 录制 URL 剥离 `ts` 和 `token` → `/api/data?page=1`
2. 回放 URL 同样剥离 → `/api/data?page=1`
3. 两者一致 ✅ 匹配成功

---

### 6.2 URL 模板转换

**用途**：将动态 URL 路径段映射为固定的模板变量，支持复杂的 URL 结构变化。

#### 配置字段

| 字段 | 说明 | 示例 |
|------|------|------|
| **匹配模板** | 使用 `{name}` / `{name*}` / `*` 描述录制 URL 结构 | `/api/user/{id}/posts/{postId}` |
| **目标模板** | 将捕获变量映射到回放 URL | `/api/user/{id}/posts/{postId}` |
| **变量正则约束**（可选）| 对特定变量指定正则 | `id: \d+`, `postId: [a-f0-9]+` |

#### 模板语法

| 语法 | 说明 | 示例匹配 |
|------|------|----------|
| `{name}` | 单段捕获（不含 `/`） | `/user/123/posts` → `id=123` |
| `{name*}` | 贪心捕获（含 `/`） | `/files/a/b/c.txt` → `path=a/b/c.txt` |
| `*` | 匹配任意单段 | `/api/*/detail` → 匹配 `/api/v1/detail` |

#### 示例

录制时有请求 `GET /api/v1/user/12345/profile`，回放时可能变为 `GET /api/v2/user/67890/profile`。

配置匹配模板：`/api/{version}/user/{uid}/profile`
目标模板：`/api/{version}/user/{uid}/profile`

匹配时 `{version}` 和 `{uid}` 可在两侧取不同值，只要结构一致即可匹配。

---

### 6.3 FUZZY MATCH (LCS)

**用途**：作为兜底策略，使用最长公共子序列（LCS）算法进行模糊匹配。当前面所有策略都无法命中时启用。

#### 配置字段

| 字段 | 说明 | 默认值 |
|------|------|--------|
| **LCS 相似度阈值** | 匹配所需的最低相似度百分比 | 95% |

#### 注意事项

- **仅作为兜底策略**：Fuzzy Match 会尝试匹配所有未命中的请求，可能会误匹配（将请求 A 的响应返回给请求 B）
- **阈值建议**：>= 85% 以减少误匹配风险
- **性能开销**：LCS 算法计算量较大，对大量 URL 的匹配可能有性能影响

---

### 6.4 内置策略

以下策略始终启用，无需用户配置：

| 策略 | 说明 |
|------|------|
| **exact** | 精确匹配。同时处理尾部斜杠的差异（`/path` ↔ `/path/` 互相匹配） |
| **protocol_swap** | HTTP 和 HTTPS 协议互换。录制时用 `http://`，回放时用 `https://` 也能匹配 |
| **strip_hash** | 忽略 URL 中的 `#fragment` 部分。录制时 `page#section1` 和回放时 `page#section2` 可以匹配 |
| **content_type_fillback** | 自动为缺失 Content-Type 响应头的资源补充类型，避免浏览器因类型未知而拒绝加载 |
| **HEAD→GET 回退** | HEAD 请求无精确匹配时自动回退到同 URL 的 GET 记录（HEAD 不需要 body，GET 返回的多余 body 会被安全忽略）。注意：**不会**反向回退（GET 不会使用 HEAD 记录，因为 HEAD 无 body） |

### 6.5 策略优先级

策略按以下扁平顺序执行（匹配即停止，不再尝试后续策略）：

```
1. exact（内置）
   ↓ 未命中
2. protocol_swap（内置）
   ↓ 未命中
3. strip_hash（内置）
   ↓ 未命中
4. 用户策略 1（按策略管理器中的排序）
   ↓ 未命中
5. 用户策略 2
   ↓ 未命中
   ...
   ↓ 全部未命中
6. content_type_fillback（内置兜底）
```

> **建议**：将精确度高的策略（QueryParams、URL 模板）排在前面，Fuzzy Match 放在最后。

## 7. 常见问题

### Q1：Player 打开 .swsonic 文件后页面显示空白或不完整？

**可能原因**：

1. **策略配置不足**：动态参数未被策略覆盖，导致请求无法匹配录制缓存。解决方法：在 Creator 中打开资源查看器，查看哪些请求 URL 包含动态参数，回到策略管理器添加对应策略后重新保存。
2. **录制数据不全**：录制时可能未覆盖所有页面交互路径。建议在录制时完整走一遍目标操作流程。
3. **CORS 限制**：某些跨域资源可能因安全策略被浏览器拦截，此类问题通常不影响回放。
4. **浏览器缓存残留**：播放器实例中积累的缓存数据可能干扰回放，可尝试 **工具 → 清除缓存**（见 [5.2 清除缓存](#52-基本操作)）后重新打开文件。

### Q2：启动 Creator 或 Player 时提示"WebView2 未安装"？

请从 [Microsoft 官网](https://developer.microsoft.com/microsoft-edge/webview2/) 下载并安装 **Evergreen Standalone Installer**。

### Q3：录制的 .swsonic 文件很大？

HTTP 响应体（特别是图片、视频、大 JS 包）会占用空间。建议：

- 录制前清理浏览器缓存
- 仅录制必要的页面操作路径
- 对于静态资源（CDN 上的库文件等），可考虑在回放时让其从网络加载（不录制这些 URL）

### Q4：回放时部分样式或图片丢失？

这通常是策略匹配不完整导致的。使用 Creator 的回放预览 + 诊断报告功能（见 [4.6 工作流五](#46-工作流五回放预览与诊断)），查看"缓存未命中"列表，补全策略后重新保存。

### Q5：调研分析和录制有什么区别？什么时候用哪个？

- **调研分析**：快速扫描（几秒），不存储响应体。用于了解网站网络结构，获取策略建议。
- **录制**：完整捕获（跟随用户操作），存储所有响应体。用于生成可回放的 .swsonic 文件。

推荐流程：先调研 → 根据报告配置策略 → 再录制 → 回放预览验证 → 保存。

### Q6：多个策略之间有冲突怎么办？

策略不会冲突，它们按优先级顺序依次尝试。如果高优先级策略匹配成功，低优先级策略不会执行。如果希望某个匹配条件优先，在策略管理器中将其上移到更高位置。

### Q7：为什么回放预览时某些请求状态码显示 "410 HEAD-only"？

这是一种特殊的未命中情况：回放时浏览器对该 URL 发出了 GET 请求，但录制数据中**仅有 HEAD 方法的记录**（无 GET 记录）。

**为什么发生**：浏览器加载资源时常会先发送 HEAD 请求探测（验证缓存、Content-Type 等），再发送 GET 请求获取实际内容。录制过程中，某些资源可能仅捕获到 HEAD 阶段的请求，而未捕获后续的 GET 请求。

**为什么不用 HEAD 记录代替**：HEAD 响应没有 body，直接返回给 GET 请求会导致页面收到空内容，可能造成渲染异常（如 Flash / SWF 文件加载失败）。因此 Sonic 不会将 HEAD 记录用于 GET 请求的匹配。

**如何解决**：
1. 重新录制，确保 GET 请求被完整捕获（触发页面完整渲染流程）
2. 如果使用了 URL 模板策略将多个 URL 重定向到同一个目标，请选择具有 GET 记录的 URL 作为目标

> **注意**：HEAD→GET 方向的回退是安全的（HEAD 响应不需要 body，多余的 body 会被忽略），此回退始终启用，无需用户干预。

### Q8：Creator 和 Player 可以同时运行吗？

可以同时运行。两者使用**独立的 WebView2 user data 目录**（Creator: `%TEMP%\sonic_creator_wv2`，Player: `%LOCALAPPDATA%\Sonic Player\instances\__player_default\webview2`），互不干扰——Creator 录制时清空自己的目录，不会影响 Player 的存档数据。详见 [3.4 Web 持久化存储与 Origin（源）](#34-web-持久化存储与-origin源)。
